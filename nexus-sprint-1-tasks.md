# Sprint 1 — Data Foundation: Tasks, Deliverables & Learning

**Companion:** `nexus-action-plan.md` (Sprint 1 section — this doc expands it with deliverables + learning goals)

**Goal of this sprint:** give the workbench a memory. Real tables for users, profiles, quests, events, and daily logs; a migration that builds them; and a seeded quest catalog you can read back over HTTP. Still single-user, still no game logic (that's Sprint 2) — this sprint is schema + plumbing.

---

## 1. Models (`app/models/`)

**Tasks**
- [✅] `user.py` — id (UUID), email (unique), display_name, avatar, role, created_at (tz-aware)
- [✅] `profile.py` — user_id FK (PK), total_xp, coins, trophies, streak_count, streak_longest, last_active, level
- [✅] `quest.py` — id (slug PK), category, title, xp, coins, stat_key, active
- [✅] `event.py` — id (UUID), user_id FK, ts (tz-aware), type, xp_delta, coin_delta, quest_id FK, meta (JSONB)
- [✅] `daily_log.py` — user_id + date composite PK (== `unique(user_id, date)`), xp_earned, quests_done (JSONB), combos (JSONB)
- [✅] Indexes: `events(user_id, ts)`, `events(ts)`, `daily_logs(user_id, date)` (the latter is free — it's the composite PK)

**Deliverable:** `app/models/` — five SQLModel table classes, all importable from `app.models`, sharing a JSON-on-Postgres/JSON-elsewhere column helper (`app/models/_types.py`) so the same models are testable against SQLite without a live Postgres.

**You'll learn**
- SQLModel: one class doubles as your Pydantic schema *and* your SQLAlchemy table
- Why `events` is append-only and `profiles`/`daily_logs` are derived, rebuildable summaries (event-sourcing lite)
- Portable column types: `JSON().with_variant(JSONB(), "postgresql")` and `sqlalchemy.Uuid` — native Postgres types, generic fallback elsewhere
- Composite primary keys as a uniqueness constraint, not just an index

## 2. Migrations (Alembic, async)

**Tasks**
- [✅] `alembic init -t async alembic` — async template, since the app's engine is `asyncpg`-based
- [✅] `alembic/env.py` — `target_metadata = SQLModel.metadata` (after importing `app.models` so every table registers); DB URL pulled from `app.config.settings`, never duplicated in `alembic.ini`
- [✅] `alembic revision --autogenerate -m "initial schema"`
- [✅] **Read the generated migration before applying it** — fixed two autogenerate gotchas by hand: missing `import sqlmodel` (needed for `sqlmodel.sql.sqltypes.AutoString` columns) and an unimported `Text` reference in the JSONB variant. Patched `script.py.mako` too, so future autogenerated migrations get the `sqlmodel` import for free.
- [✅] `alembic upgrade head` → inspected tables (verified against a throwaway SQLite DB — see note below)
- [✅] `alembic check` (autogenerate diff against the applied schema) → **no drift** — the migration matches the models exactly

**Deliverable:** `alembic/` wired to the real models, one clean initial-schema migration, verified to apply and match with zero diff.

**⚠️ Verified against SQLite, not Postgres.** Docker Desktop still isn't installed on this machine (same blocker as Sprint 0), so `alembic upgrade head` was run against a throwaway local SQLite file as a stand-in — same migration file, same models, just a different engine underneath. This is why the JSON-variant column trick from §1 matters: it let the *real* migration get a *real* dry-run without Postgres. **Once Docker's installed:** run `docker compose up -d`, then `alembic upgrade head` for real, and ideally `alembic check` again against Postgres specifically (JSONB and a couple of type nuances only show up there).

**You'll learn**
- Alembic's async template: wrapping `run_sync` around a sync migration function so it works with an async engine
- Autogenerate isn't magic — it diffs live DB vs. metadata, and needs a real connection to do it (which is *why* it needed a stand-in DB here)
- `alembic check` as a CI-friendly way to catch model/migration drift before it becomes a bug

## 3. Seed the catalog (`app/data/`, `scripts/seed.py`)

**Tasks**
- [✅] `app/data/quests.yaml` — starter catalog across Main / Side / Health / Leisure / Penalties, with xp/coins/stat_key per quest
- [✅] `app/data/combos.yaml`, `shop.yaml`, `achievements.yaml` — data files for Sprint 2's engine to read; no DB table yet (nothing in the Sprint 1 model list needs one)
- [✅] `scripts/seed.py` — idempotent upsert by `id`, safe to re-run
- [✅] `GET /quests` router — returns the catalog grouped by category, inactive quests hidden

**⚠️ Not ported from a prototype.** The action plan says "port every quest from the prototype," but no prototype exists in this repo or workspace. Per your call, this is a **hand-written starter set** — real categories and mechanics from `level-up-requirements.md`, placeholder ids/titles/numbers. Swap in your real catalog whenever; nothing downstream (models, seed script, router) hardcodes these values.

**Deliverable:** `python scripts/seed.py` populates `quests` from YAML, idempotently; `curl /quests` returns the full board grouped by category.

**You'll learn**
- Why the catalog lives in YAML + DB, not in frontend code — server-authoritative XP starts here, not in Sprint 2
- Idempotent upserts (`match by id, update in place`) vs. "just re-insert and hope" — the difference is what makes `scripts/seed.py` safe to run on every deploy
- FastAPI response models (`Pydantic` shapes, not raw dicts) and dependency injection (`Depends(get_session)`) for DB access per-request
